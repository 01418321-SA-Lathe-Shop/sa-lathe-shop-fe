# UC Test Brief — ทดสอบ UC1–UC12 บน Local พร้อมแคปหน้าจอสำหรับรายงาน SA

> วางไฟล์นี้และ `UC1-UC12-test-guide.html` (คู่มือทดสอบ) ไว้ใน `docs/uc-testing/` ของ repo
> แล้วสั่ง Claude Code: **"อ่าน docs/uc-testing/uc-test-brief.md แล้วทำตาม เริ่มจาก Phase 0"**

## เป้าหมาย
ทดสอบเว็บไซต์บนเครื่อง (Local) ว่าทำงานตรงตาม Use Case UC1–UC12 ในคู่มือ `UC1-UC12-test-guide.html`
ทุก "ขั้นตอน", ทุก "ผลที่คาดหวัง" และทุก "กรณีผิดพลาดที่ต้องลอง" ต้องมีภาพหน้าจอเป็นหลักฐาน
ภาพจะถูกนำไปใส่ในรายงานโครงงานวิชา Systems Analysis and Design หัวข้อ
"การทดสอบโปรแกรมทำงานตาม UC description" (ตาราง: uc id | uc name | capture screen + คำบรรยาย "รูปที่ N ...")

## ข้อมูลระบบ (Local)
- Frontend: `http://localhost:3100` (Next.js, เปิดอยู่แล้ว)
- Backend: `http://localhost:8080` (Go) — ตรวจจาก `NEXT_PUBLIC_API_BASE_URL` ใน `.env.development.local` ถ้าไม่ใช่พอร์ตนี้
- เข้าสู่ระบบ: หน้า `/login` กดปุ่ม **"บัญชีทดสอบ Local · เข้าสู่ระบบทันที"** แล้วเลือกบัญชี (ไม่ต้องใส่รหัสผ่าน)
  - ระหว่างทดสอบเปลี่ยนบทบาทได้ด้วยเมนู **"สลับบัญชีทดสอบ"** ในแถบด้านข้าง
  - บัญชี: `somchai` (ลูกค้าบุคคล), `nida.company` (เจ้าของบริษัท), `ploy.company` (สมาชิกบริษัท),
    `anan.staff`, `kittipong.staff` (Worker), `pim.admin` (Admin)
  - UC12 ต้องใช้ Super Admin: ตรวจใน seed ของ backend ว่าบัญชีไหนเป็น Super Admin และเข้าแบบทดสอบได้หรือไม่ ถ้าไม่ได้ให้ถามผม
- ภาพที่ถ่ายจะเห็น URL เป็น `localhost:3100` (เหมือนรายงานตัวอย่างที่ใช้ `localhost:3000`) ถือว่าใช้ได้

## กฎสำคัญ
1. **ห้ามแก้โค้ดแอปเพื่อให้เทสผ่าน** ถ้าผลจริงไม่ตรงกับผลที่คาดหวัง ให้บันทึกเป็น FAIL พร้อมภาพหลักฐาน แล้วทำต่อ
2. **ภาพไม่ใช่หลักฐานว่าผ่าน** ทุกขั้นต้องมี assertion ใน Playwright และหลังรันเสร็จต้องเปิดดูภาพจริง (Read รูป) ว่าตรงกับคำบรรยาย
3. ก่อนเริ่มรัน: สำรองฐานข้อมูลทดสอบ (dump) หรือหาคำสั่ง reset + seed ของ backend ไว้ เพื่อรันซ้ำจากสถานะสะอาดได้
   ห้ามแตะฐานข้อมูล Production
4. ข้อมูลที่เทสสร้างให้ขึ้นต้นด้วย `[UCTEST]` เพื่อให้ดูออกในภาพว่าเป็นข้อมูลทดสอบ
5. ห้ามหยุด/รีสตาร์ต backend หรือแก้ข้อมูลในฐานข้อมูลตรง ๆ โดยไม่บอกผมก่อน

## Phase 0 — สำรวจและวางแผน (ยังไม่รันเทส)
- อ่านคู่มือ `UC1-UC12-test-guide.html` (ข้อมูลอยู่ในตัวแปร `UCS` ใน `<script>`) และโค้ด frontend/backend เพื่อหา route, ปุ่ม, selector, และวิธี login บัญชีทดสอบ
- ตรวจว่า `http://localhost:3100` และ backend ตอบสนองจริง
- ติดตั้ง `@playwright/test` ใน `docs/uc-testing/` (หรือ `e2e/`) ถ้ายังไม่มี ตั้ง `baseURL: 'http://localhost:3100'`
- เขียน helper `loginAs(page, username)` ที่กดปุ่มบัญชีทดสอบ Local แล้วเลือกบัญชี
- สร้าง `docs/uc-testing/plan.md`: ตาราง UC → ขั้นตอน → ภาพที่จะถ่าย → ชื่อไฟล์ → คำบรรยายภาษาไทย
- ระบุวิธีทดสอบกรณีพิเศษ เช่น
  - "ปิด backend แล้วโหลดหน้า" (UC1) → ใช้ `page.route('**/<api-path>/**', r => r.abort())` จำลอง backend ล่ม (ไม่ต้องปิด backend จริง)
  - "ส่งหลักฐานเลย 14 วัน" (UC4) → เสนอวิธี เช่น เลื่อนวันครบกำหนดในฐานข้อมูลทดสอบด้วย SQL เฉพาะรายการ `[UCTEST]` (ขออนุมัติผมก่อน) ถ้าทำไม่ได้ให้ SKIP พร้อมเหตุผล
  - "แก้ไขพร้อมกัน 2 แท็บ" (UC2) → ใช้ 2 browser context (anan + kittipong)
  - "ไฟล์เกิน 100 MB" → สร้างไฟล์ dummy ชั่วคราว ห้าม commit
  - "ปฏิเสธครบ 6 ครั้ง" (UC3) → ต้องให้ Worker ส่งฉบับแก้ไขสลับไปมา เขียนเป็น loop
- **หยุดและส่ง plan.md ให้ผมดูก่อน** แล้วค่อยไป Phase 1

## Phase 1 — เขียนเทส
- 1 ไฟล์ต่อ UC: `tests/uc01.spec.ts` … `tests/uc12.spec.ts` รันแบบ serial (`workers: 1`, `test.describe.configure({ mode: 'serial' })`) เพราะข้อมูลต่อยอดกัน
- เขียน helper `shot(page, { uc, step, kind, slug, caption, highlight? })` ที่:
  - ถ่ายภาพ viewport 1440×900, `deviceScaleFactor: 2` (คมพอสำหรับเอกสาร)
  - รอให้หน้าโหลดเสร็จ (ไม่มี spinner/skeleton) ก่อนถ่าย
  - ถ้ามี `highlight` ให้วาดกรอบสีแดงรอบปุ่ม/ช่องที่กำลังจะกดก่อนถ่าย แล้วลบออก (สอดคล้องกับคำบรรยาย "กดเลือกที่ปุ่ม ...")
  - แสดงแถบ URL เล็ก ๆ ด้านบนภาพ เพื่อให้รู้ว่าอยู่หน้าไหน เหมือนภาพในรายงานตัวอย่าง
  - บันทึกบรรทัดลง `manifest.json`
- ใน 1 ขั้นตอนให้ถ่ายอย่างน้อย:
  - `A` = action (หลังกรอกฟอร์ม / ก่อนกด โดยไฮไลต์ปุ่มที่จะกด)
  - `R` = result (ผลที่คาดหวังปรากฏบนจอ เช่น toast, สถานะใหม่, ข้อความ error)
- กรณีผิดพลาดใช้ `N`

  - `S` = ขั้นตอนหลักตามลำดับในคู่มือ, `N` = กรณีผิดพลาดตามลำดับในคู่มือ (กรณี N ไม่ต้องมี -A/-R ถ้าภาพเดียวพอ)
  - ถ้าขั้นเดียวต้องหลายภาพ ใช้ `A1`, `A2`, …
- ชื่อไฟล์เป็นอังกฤษล้วน (กันปัญหา encoding ใน Word/Git) ส่วนภาษาไทยอยู่ใน manifest

### manifest.json (1 รายการต่อภาพ)
```json
{
  "file": "UC01_register-and-submit-request/UC01-S01-A_register-individual-fill-form.png",
  "uc": "UC1", "uc_name": "ลงทะเบียนลูกค้า สมาชิกบริษัท และส่งคำขอผลิต",
  "step": "S01", "kind": "action",
  "role": "ลูกค้า (บุคคลทั่วไป)", "url": "/register",
  "caption_th": "กรอกชื่อผู้ใช้ ชื่อ ที่อยู่ และรหัสผ่าน 12 ตัวอักษร แล้วกดปุ่ม “สมัครสมาชิก”",
  "expected_th": "สมัครสำเร็จและเข้าสู่ระบบลูกค้าได้",
  "status": "PASS | FAIL | SKIP", "note": ""
}
```
คำบรรยายเขียนแบบรายงานตัวอย่าง: "กดเลือกที่ปุ่ม “…”", "กรอกข้อมูลให้ครบแล้วกดปุ่ม “…”", "ระบบแสดงข้อความ …"
ใช้ชื่อปุ่มตามที่ปรากฏบนหน้าจอจริง
ขั้นตอนที่เป็นการกดปุ่มบัญชีทดสอบ/สลับบัญชี ไม่ต้องใส่ในรายงาน (เป็นเครื่องมือทดสอบ ไม่ใช่ฟังก์ชันของระบบ) แต่ให้ระบุบทบาทใน `role`

## Phase 2 — รัน
- รันทีละ UC ตามลำดับ UC1 → UC12 และตรวจภาพหลังจบแต่ละ UC ก่อนไป UC ถัดไป
- ถ้าเทสพังเพราะ selector/timing (ไม่ใช่บั๊กของแอป) ให้แก้เทสแล้วรันใหม่ได้
- ถ้าพังเพราะแอปทำงานไม่ตรง UC → FAIL + ภาพ + note อธิบายสั้น ๆ แล้วไปต่อ
- ถ้าต้องรันใหม่ทั้งชุด ให้ reset ฐานข้อมูลทดสอบกลับสถานะ seed ก่อน (ตามที่เตรียมไว้ใน Phase 0)

## Phase 3 — ตรวจและสรุป
- เปิดดูทุกภาพ: ภาพไม่ว่าง ไม่ติด loading เห็นผลที่คาดหวังจริง และคำบรรยายตรงกับภาพ
- สร้าง `results.csv` (uc, step, kind, file, status, note) และสรุปจำนวน PASS/FAIL/SKIP ต่อ UC
- สร้าง `UC-test-report.docx` รูปแบบเดียวกับรายงานตัวอย่าง:
  - หัวข้อ "การทดสอบโปรแกรมทำงานตาม UC description"
  - ตาราง 3 คอลัมน์: uc id | uc name | capture screen
  - ใต้ภาพแต่ละภาพ: "รูปที่ N {caption_th}" (นับเลขรูปต่อเนื่องทั้งเอกสาร เริ่มเลขได้จากตัวแปร `FIGURE_START`)
  - ฟอนต์ TH Sarabun New 16pt (หรือตามที่ผมกำหนด) ภาพกว้างพอดีคอลัมน์
  - เพิ่มบรรทัด "ผลการทดสอบ: ผ่าน/ไม่ผ่าน" ใต้ภาพ result (ดีกว่ารายงานตัวอย่าง)

## ส่งงาน
สรุปให้ผม: จำนวนภาพ, PASS/FAIL/SKIP ต่อ UC, รายการ FAIL พร้อมไฟล์ภาพ, และ path ของ docx
